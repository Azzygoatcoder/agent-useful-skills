# v1.5.1 — 发布改由 CI 负责：Release 开始带产物

## 概览

本仓库过去的 Release **全部是 0 产物**（v1.0.1 到 v1.5.0，一个不落）。`pyproject.toml` 早就声明了一个正经的包
（`agent-useful-skills` + 13 个 console script），却从来没构建、也没挂过任何 sdist / wheel。

本版把发布改由 CI 负责：**推 tag → 构建 → 建 Release → 挂产物**。这也是本仓库第一个带产物的 Release。

| 组件 | 版本变化 |
|------|---------|
| 根快照（`pyproject.toml`） | 1.5.0 → **1.5.1** |
| 插件 `dev-workflow` | 2.0.1 → **2.0.2**（见上一提交） |

## 新增 `.github/workflows/release.yml`

推 tag 触发，做三件事：

1. **复用 `verify.yml` 的全部门禁** —— 不在红的提交上发版。之所以用 `workflow_call` 复用而不是抄一份检查清单：
   抄的话，`verify.yml` 以后加了新门禁，发版这条路会**静默不跑**它
2. `python -m build` 产出 **sdist + wheel** 并挂到 Release
3. notes 优先读 `release-notes/<tag>.md`（就是本文件），找不到则 `--generate-notes`

## 为什么必须是 CI 建，而不是手跑

这条来自另一个项目的真实事故，本版把它固化成了工作流的写法：

> 手跑 `gh release create` 与 tag 触发的 workflow **抢跑**。workflow 的创建步骤看到 Release 已存在便跳过
> （幂等本身没错），但**上传产物**那步挂在创建步骤的输出上（`if: steps.create.outputs.upload_url`）
> → 一并跳过，最终留下一个**有 notes、看着正常、却没有任何产物**的 Release —— **而且不报错**。

所以本工作流刻意写成两条规则：

- **① 创建幂等**：Release 已存在就跳过创建，不算失败
- **② 上传无条件**：`gh release upload ... --clobber` 独立成步，**绝不**挂在创建步骤的输出上

推论：**不要手动 `gh release create`**。要发版就推 tag。若已抢跑，`gh release delete`（**不会删 tag**）+ 重跑本工作流即可修好。

## 配套改动

- **`release-notes/`（新）**：notes 落点 + 约定说明。必须**在打 tag 之前提交** —— CI 是在 tag 指向的
  commit 上 checkout 的，之后补的文件这次读不到
- **`verify.yml`**：加 `workflow_call`，供 release.yml 复用
- **`.gitignore`**：补 `build/` 与 `dist/`（开始构建了；`*.egg-info/` 原本就已忽略）
- **根 README** 新增「发布」一节；**`VERSIONING.md`** 写明发版方式，并修掉两处**陈旧的 `release-skill` 引用**
  （该技能 2026-09-12 已并入 `dev-workflow`；根级 `.md` 不在校验器扫描范围内，所以一直没被抓到）
- **`dev-workflow` 的 `release.md`**：新增「发布机制：先确认由谁创建」一节、
  第 5 步「核对产物（必做）」、恢复步骤与 Edge cases —— 并把本仓库标注为其「CI 自动」型的实例
