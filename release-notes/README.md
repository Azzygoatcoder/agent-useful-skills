# Release Notes

`release.yml` 在创建 GitHub Release 时会**优先读这里的 `<tag>.md`**，找不到就用 `--generate-notes` 自动生成。

## 约定

- 文件名 = tag 名：`v1.5.1.md`
- **必须在打 tag 之前提交** —— CI 是在 tag 指向的那个 commit 上 checkout 的，之后补的文件这次发版读不到
- 首行若是 H1（`# ...`），就拿它当 Release 标题；否则标题用 tag 名
- 找不到文件不会让发版失败（回退到自动 notes），所以这是**可选增强**，不是必填项

## 为什么要有这个目录

本仓库的 Release 一直带手写的分主题说明（哪些是修复、哪些是刻意不采纳、门禁结果），
这比 `--generate-notes` 自动列的 commit 列表有用得多。但 `release.yml` 是 CI 里跑的，
读不到开发机上的临时文件 —— 所以要有一个**随仓库走**的落点。

## 一个已知限制：产物**不可复现**

**同一个 tag 重跑发布工作流，产物的字节会变**（sdist 尤其）。实测：连跑两次 sdist，
哈希不一致；加上 `SOURCE_DATE_EPOCH` 后**仍然**不一致 —— 因为 setuptools 的 sdist 用
**文件 mtime** 填 tar 条目，`SOURCE_DATE_EPOCH` 覆盖不了它。

所以：

- **别把「重跑发布」当无害操作**：它会把已挂的产物替换成内容等价、哈希不同的新文件
  （`gh release upload --clobber` 的语义就是替换）
- 若有人按哈希固定产物，重跑会让他们失配
- 但**补建 Release / 补挂缺失产物**时，重跑正是设计意图 —— 只需意识到哈希会刷新
- 真要可复现构建，得把 tar 条目的 mtime 固定下来（自定义 sdist 或 `--mtime` 工具链），
  目前**没做**，也没有假装做了（试过 `SOURCE_DATE_EPOCH`，无效，故未写入工作流）

> 另注：工作流是在 **tag 指向的那个 commit** 上构建的。所以改了打包配置之后，
> 旧 tag 重跑只会复现旧配置的产物 —— 修复要等下一个 tag。

## 写法

参考任意一版 Release 的正文，通常包含：

- 版本号变化（根 / 各插件）
- 分主题的变更（不是按 commit 顺序罗列）
- **明确的取舍**：哪些**没**做、为什么
- 门禁结果（跑了哪些检查、全绿）
- 自上一个 tag 的完整提交列表 + `compare` 链接

> 不写也不会挡发布 —— 但写了就有。首行给了标题就能保住以前那种
> `v1.5.1 — 一句话主题` 的标题样式。
